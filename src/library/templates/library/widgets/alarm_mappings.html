Help — status → alarm mappings

Source is the decoded field to inspect — defaults to status (the wmbusmeters convention). For LoRaWAN, use the JS-codec output field name. New rows copy the previous row's source.

Match is evaluated per the config's match type:

Type Device reports Match Alarm active when…
flag status: "LEAKING BATTERY_EOL" LEAKING token appears in the flag list — several alarms can fire from one field (wM-Bus / wmbusmeters)
equals error_code: 3 · leakage_status: "leak" 3 · "leak" value equals match exactly — one value, one state (LoRaWAN error codes, enums, booleans)
mask status_byte: 56 (0b00111000) {"mask": 48, "pattern": 48} (value & mask) == pattern; pattern defaults to mask ("bits set"). Like flag, but over bits — several alarms per byte (LoRaWAN status bitmasks, e.g. Axioma bit patterns)

Alarm points at the shared L1 catalogue (/alarms/) — severity and description are defined there, not per mapping. Need a new alarm? Add it in the catalogue (or type its key in the JSON view — unknown keys are auto-created on save). Legacy entries with inline severity/description and no alarm still work and are editable in the JSON view.

Flags not listed here fall back to the instance's built-in driver registry, then to a generic warning.
